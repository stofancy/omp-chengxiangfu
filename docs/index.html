omp 插件 · 调度台 · 一篇实践总结的图解

注意力稀缺下的harness 调度

一个人同时推进几件事时，注意力花在两条线上：在几个 agent 会话之间派活、验收；在 Slack、PR、工单之间来回查看，再把相关的内容转述给对应的会话。调度台把这两条线上的调度交给 harness，只有需要你定的事才打扰你。

背景是一段示意动画：暖色的点是你的注意力，冷色的线是外部输入和子代理的交回。人自己调度时，每一条都直接到你这里；交给调度台后，大部分在外圈被过滤，或者交给各任务的负责 agent，只有要你定的事才到你这里。

01问题

注意力花在两条线上

过去一年，编码 agent 已经能在很少人工干预的情况下做完一件具体的事。瓶颈随之移动：一件事做得好不好，看模型；同时推进几件事，看人的注意力。

第一条线

调度 agent

记住每件事在哪个会话、到了哪一步，决定什么时候让谁去做，做完了还要看懂、验收。

在会话之间切换；在用的日子平均每天 6.3 次，最多一天 22 次
46次

29次

33条
消息只有一句批准；另有 53 条在问「这是什么」「这是谁」

第二条线

盯外部输入

Slack 的频道、thread 和私信，PR 的评论和评审，工单，各种提醒。人要轮流去看，判断哪条和哪件事有关，再转述给对应的会话。

约9条
消息是在告诉 agent「有回复了」；他还得自己去问「PR review 有更新了吗？」
18次

口径：插件出现之前的六周（2026 年 10 月 6 日到 11 月 17 日），作者在 omp 里开了 52 个会话，有 27 天在用，一共发了 798 条消息；每天同时推进的会话中位数是 3 个。只统计 omp 的会话；「切换」指把所有用户消息按时间排好后，相邻两条落在不同会话；「有回复了」这类按关键词检索，是近似值。

02缺口

harness 缺的那一层

Claude Code、Codex CLI、omp 这类 harness 默认一个人驱动一个会话。它们已经有子代理：主会话可以派出在后台跑的 agent，做完把结果交回。缺的是把几件事、几个输入源串起来的那一层，现在由人来补。

  1. harness 默认输入来自人打的字

    人在补在各个输入源之间来回看，判断和哪件事有关，再转述给对应的会话

    调度台会话外的接收程序把外部输入写进收件箱，按任务归位；噪音大的频道先过滤输入

  2. harness 默认一件事放在一个会话里

    人在补在会话之间切换，记住每件事在哪、到了哪一步

    调度台一个主会话做唯一入口，每个任务一个长期的负责 agent调度

  3. harness 默认状态在会话的上下文里

    人在补换会话、上下文被压缩以后，把背景重讲一遍

    调度台程序维护的任务表，每次请求附上摘要任务表

  4. harness 默认每一轮都给人一段回复

    人在补逐条读，判断要不要管

    调度台每条回复标明为什么在说话；待定的事固定显示；提问编号界面

  5. harness 默认做完由做的人自己说

    人在补逐个验收

    调度台没见过过程的审查者重跑；没通过就记不成完成可信

  6. harness 默认约定写进提示词

    人在补一遍遍纠正同样的错

    调度台能用程序检查的交给程序；纠正先变成提问，人同意才写成规则规则

这些默认做法放在「一个人驱动一个会话」的场景里都合理，一个人同时推进几件事时才变成负担。DeepSeek Harness 团队在《Exploring Super-agent Design》里也观察到，一个人通常只能同时盯住三到五个活跃会话；把外部输入当成触发器接进 agent，也是那篇文章提出的方向。调度台是在 omp 上的一次实践。

一个上午，三件事

同时推进三件事，外面不断有消息进来，你大半个上午在开会。跟着走一遍，看你的注意力花在哪、省在哪。点「下一步」，或者让它自己播放。

04做法

每一块补一个缺口

派子代理、给子代理发消息、续会话后叫醒子代理，omp 都自带。调度台只补 omp 没有的东西，不另造守护进程，也不另造看板。

调度

主会话管全局，负责 agent 干活

补的是「一件事放在一个会话里」

  • 主会话研判、立项、统筹、验收、汇报；自己不读代码，也不去查外部系统，因为调查也算干活。
  • 每个任务一个长期的负责 agent。这个任务的上下文在它手里，怎么干由它定。
  • 它只管任务之间的关系，不拆单个任务，更接近 DeepSeek 文章里的路由层。
踩过的坑

作者说过一句「什么长期负责人……都是次要的」。我们一度把它理解成不要负责 agent 这一层，删掉以后又加了回来：他的本意是做法可以换，每个任务有一个负责人这件事不变。

任务表

程序记账，模型判断

补的是「状态在会话的上下文里」

  • 全局一本只追加的记录，每一行是一次变化；给人看的视图由程序生成，主会话每次请求都附一份摘要。
  • 你只回「1 做 2 不做」时，程序直接把它记成决定，不经过模型转述。
  • 没有审查者记下的「通过」，任务记不成完成。这是插件唯一拦截的操作。
踩过的坑

早期每个会话有自己的一本账，换一个会话就对不上。状态放在模型的记忆里，会忘，也会编。

输入

在会话之外接收，先过滤再叫醒

补的是「输入来自人打的字」

  • 接收程序只读外部系统，只往收件箱写谁、在哪、链接，不写原文。现在接了 Slack、PR 和本地提醒。
  • 能按订阅归位的，程序直接归；归不到的交主会话研判。
  • 噪音大的频道先让便宜的模型分拣；模型调用失败，这一批全部送出，宁可多打扰也不漏。
踩过的坑

补读一页读 200 条，网络一抖响应就被截断。消息没丢，但大频道的消息最长晚了 4 个多小时。后来改成每页 50 条、失败重试。

注意力界面

少说、说清、问得好答

补的是「每一轮都给人一段回复」

  • 每条回复上方一行标头，说明这一轮为什么在说话。
  • 输入框上方的固定区放等你定的事、在跑的 agent、接收程序的故障。
  • 提问编号，一次最多三件，附推荐和不选的后果。下一节可以点着试
踩过的坑

一个下午，回复里「不用你处理」出现了 30 次。告诉作者「不用你处理」，本身就在占用他的注意力。

可信

约束和验收

补的是「做完由做的人自己说」

  • 主会话和所有子代理都带几条约束：不 force push，不推主分支，白名单以外的远端写入先问。
  • 负责 agent 报整个任务做完，主会话另派一个没见过过程的审查者，重跑、对照完成判据。
  • 把工作内容发给 omp 模型配置以外的第三方服务，也算远端写入。
踩过的坑

有一次，结果在审查还没出结论时就发给了同事，审查判了不通过，只好再发一条更正。现在审查者在跑的时候，负责 agent 的每次请求都会附一句提醒。

规则

规则越少越好，纠正变成机制

补的是「约定写进提示词」

  • 能用程序检查的就不写规则：回复超长、出现内部代号，交给程序提醒。
  • 机制自己制造噪音，就删掉它。
  • 你纠正一次，先登记成一个编号提问；你同意了才写进规则文件。
踩过的坑

有个下午作者没有重启会话：磁盘上的规则已经是新的，在跑的代码还是旧的，那个下午有 27 条回复在解释「这在你的授权范围内」。现在规则和代码在会话启动时一起读入，插件一更新，固定区就提示重启。

06方法

用真实使用复盘，一轮一轮改

这几天的改进几乎都来自复盘，很少是事先设计好的。每一轮这样走：

  1. 取一段真实使用的时间窗。
  2. 先确认那段时间跑的是哪版代码。有一轮复盘发现作者那天下午根本没重启，跑的是前一晚的代码，中午修的东西一样都没生效。没有这一步，后面的结论会全错。
  3. 发话、回复、被叫醒回合的占比、纠正、提问和决定、交回送达、成本。注意力统计做成了一个只读的技能，按天、按任务汇总。
  4. 逐段看关键回复和事件，列出得与失，每条带时间和原话。比如「不用你处理」出现 30 次，读下来的判断是：主会话被叫醒以后，觉得总得说点什么。
  5. 一条失对应一个改动，优先改程序。指不回一条失的改动不做。
  6. 单元测试；拿真实数据回放；在 tmux 里开一个真的 omp，看真实界面；交给一个没参与过程的审查 agent。最后一道几次都抓到了真问题。
  7. 合并、部署、提示重启。上线以后，下一轮复盘就是对这一轮的检验。

十条原则

  1. 注意力是预算，要记账。两条线都记；每个机制先算它替你省了多少注意力，自己又花了多少。
  2. 一个入口，按任务分人。你只跟主会话说话，外部输入也先到主会话，再按任务交给负责 agent。
  3. 程序记账，模型判断。状态、计数、送达、拦截交给代码；归属、值不值得打扰、结果站不站得住交给模型。
  4. 能用程序就不加规则。机制制造噪音，就删掉。
  5. 用宿主已有的，只补缺的。
  6. 先过滤，再叫醒。能按订阅归位的不用模型，剩下的先让便宜模型分拣，失败了宁可多送。
  7. 打扰要可回答。一次最多三件，编号，一两个字能答，问之前先查记录。
  8. 验收不靠自述。完成判据立项时写好，没见过过程的审查者重跑，审查出结论前不往外发。
  9. 进来的不可信，出去的有闸门。收件箱只写谁、在哪、链接；远端写入先问，发给第三方服务也算。
  10. 故障要看得见，版本要对得上。每个接收程序都报健康状态；代码和规则一起加载。

这些想法大多有出处：DeepSeek 的 Super-agent，Grok Bot 的社区实践，OpenClaw，Factory 的 Missions，Hermes 的看板，omp 官方的 roboomp。我们做的，是把它们放到「一个人、一个终端里的 omp 会话」这个约束下落地，再用真实使用一轮轮检验。

08规划

现状和规划

接下来几周

先用起来，量清楚

现在最大的风险，是一直在造它而不去用它。

  • 冻结一段时间。代码只修 bug，提示词的每次改动都记下来，否则效果没法归因。
  • 两条线分开记账。输入线记进来多少、拦下多少、真正需要看的多少；调度线记每个任务花了多少发话、决定和纠正。
  • 和插件之前比。把切换次数、「有回复了」的次数按同样的方法再统计一次，并算出每个任务的花费。
  • 定退出标准。用满一段时间后，如果每个任务花的注意力并不比以前少，就砍到只剩任务表和外部输入两样。

输入线接更多来源，每个都先过滤

  • Slack 实时推送和定时补读
  • PR 的评论、评审、投票（GitHub、Azure DevOps）
  • 到期提醒
  • 按订阅归位
  • 噪音大的频道先分拣
  • 每个来源报健康状态
  1. 先补和现有来源挨着的。CI 结果跟着 PR 一起报；任务订阅的工单有新评论、状态变了、指派给了你，就写进收件箱。
  2. 再接日历和邮件。会议邀请和外部回复是另两类常见的打断；日历还能用来「提前做」，会前由负责 agent 把材料整理好。
  3. 每个源都走快慢两条路。明确找你的、任务订阅的直接送；已知可以忽略的只记日志；剩下的才交给便宜模型分拣。
  4. 订阅覆盖所有来源。任务能登记工单号、邮件会话、日历事件，程序按登记归位。
  5. 能推送的源用推送，其余轮询，带重试和健康状态。
  6. 「提前做」推广开来。某类输入一进来，负责 agent 先在后台动手，复现问题、起草回复，有结果才说话。
  7. 回复回到原处。在 Slack 里回得短，在 PR 里回得有条理；照样过远端写入的闸门。

调度线少打扰，能自己接上

  • 一本任务表
  • 每个任务一个负责 agent
  • 完成前独立审查
  • 被压住的交回由插件送达
  • 久未交回时叫醒主会话
  1. 被叫醒的回合少说话。由程序按交回的类型决定要不要出现在对话里，「进展」和「无需处理」只进任务表和固定区。这是目前最大的噪音来源。
  2. 输入直送负责 agent。如果 omp 开放了让插件给子代理投递消息的接口，外部输入就不用再经过主会话。
  3. 按进展判断卡没卡住。定时让便宜模型看一眼各负责 agent 最近在做什么：在推进、在空转，还是跑偏了。
  4. 远端写入从记录变成闸门。写入走宿主的工具或钩子，带白名单和审批队列。
  5. 任务收尾。PR 合并后自动关任务、清理工作副本、归档相关的外部输入。
  6. 离开终端也能批。omp 自带的远程协作可以在手机浏览器里对话，把编号提问接上去。
  7. 版本和兼容。打 tag，写变更说明；任务表的记录格式只加字段，不改旧字段的含义。

有些缺口应该由 harness 自己补

这一层长远看应该进到 harness 本身，插件越来越薄。想提给 omp 上游的能力：

  • 外部输入能直接进一个活着的会话；会话关着时先排队，续上后再送
  • 插件能给子代理发消息，子代理能领取归给自己的输入
  • 交回带类型，宿主据此决定要不要打扰人
  • 任务状态和子代理能跨会话找回
  • 原生的定时任务
  • 回复发出前、交回送达前，有可以挂检查的钩子

往深走

把一个人的这两条线做到离开一天回来，一屏看懂，几个字批完。这条路上最值钱的是评估方法：注意力怎么量，对照怎么做。

往宽走

从一个人到一个小组，共享任务表，个人的调度器之间互相转交。主要问题会变成上下文的边界和权限。

往下走

从插件变成常驻服务，机器睡着了也能推进。对一个人来说这一步不急，等真有「终端关着也要推进」的需求再做。

注意力稀缺时，人在替 harness 做两件事：
在 agent 之间调度，在输入源之间收发。

调度台把这两件事的大部分交给了程序和模型，人只处理需要他定的部分。还没解决的有三件：被叫醒的回合话太多，花费没有降，省了多少注意力还没有对照。长远看，这一层应该由 harness 自己提供。
